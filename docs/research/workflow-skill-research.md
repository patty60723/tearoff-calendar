# AI-Assisted Development Workflow — 研究紀錄（P7-3、Branch Audit）

> 日期：2026-11-03　來源：墨丸 V3 P7-3（狀態一致性）、P7-4a 併入、PR #3、Branch Audit。
> 性質：**研究階段的觀察**，不是最終 Skill。每條都只有這一個專案的證據；標「成熟」的只代表在這裡反覆有效，仍需其他專案驗證。墨丸專用的做法不寫成通用規範。
> 規模：**Lite**（原型、短期工具）、**Standard**（持續維護的個人專案）、**Extended**（多人協作或高風險）。
> 分類：**Universal**（跟規模、技術無關）、**Scale-dependent**（值不值得看規模）、**Stack-specific**（綁技術，例如 Android／Robolectric）、**Project-specific**（綁這個專案或這個執行環境）。

## 候選規則

### R1. 一致性檢查從「實際輸出」讀狀態，不拿設定值自己組預期

- **問題與案例**：既有測試把小工具的圖跟「用設定值重畫一張」比，等於拿同一份設定比兩次；如果某個畫面根本沒讀到新設定，這種測試仍可能通過。P7-3 改成：在真正畫圖的地方加測試用回報（正式執行時是 null），讀「畫面上那張圖當時用了什麼參數」，再用那組參數重畫、逐像素相同才算數。
- **做法**：只在輸出點加一個可觀察的掛勾（不改行為），測試讀掛勾＋驗證可重現。
- **收益**：找到一個真的不一致（換城市時故事卡的天氣），而既有的零散測試都沒抓到。
- **成本**：正式程式多 3 個掛勾（約 28 行）；測試要處理「同一張圖對到多組參數」的歧義。
- **分類**：原則 Universal；掛勾的實作 Stack-specific。
- **Lite／Standard／Extended**：否／是（多個顯示位置共用狀態時）／是。
- **成熟度**：中。需要在非圖形輸出（例如 API 回應、報表）的專案驗證同樣有效。
- **待驗證假設**：「測試用掛勾不改行為」在其他語言／框架能同樣低成本做到，而且審查者接受正式程式裡有這種掛勾。

### R2. 先讓測試重現問題，再修

- **案例**：換城市的不一致，先推修正前的測試讓 CI 紅（#174：「故事卡 expected NONE but was RAINY」），再推修正（#176 綠）。
- **收益**：證明測試真的抓得到；修正的必要性有紀錄。
- **成本**：多一輪 CI（約 4 分鐘）。
- **分類**：Universal。　**L／S／E**：建議／是／是。　**成熟度**：高（本專案 P7-1、P7-2、P7-4a、P7-3 都有效）。
- **待驗證**：CI 很慢（> 30 分鐘）的專案，是否改成本地重現就夠。

### R3. 把「應該相同的底層狀態」和「刻意不同的顯示規則」寫成規則表

- **案例**：日曆頁停在昨天時不畫今天的天氣、App 停在前景跨午夜時日曆頁暫時不動——如果沒寫下來，一致性測試會誤報，或有人「修」掉刻意的行為。P7-3 列了 9 條，其中一條（小工具一律顯示今天）原本只是既有行為，因此被提出來變成正式決策 D-55。
- **收益**：測試的斷言直接對應規則；隱性行為被提出來決定。
- **成本**：寫規則表、每條找依據。
- **分類**：Universal（多個呈現位置的系統）。　**L／S／E**：否／是／是。　**成熟度**：中高。
- **待驗證**：規則數量很多時（數十條）是否仍能維護。

### R4. 組合測試明說「代表性組合」，不宣稱完整排列

- **案例**：4 日子 × 9 天氣 = 36 種，其他維度（頁數、裝備、撕頁、Reduced Motion）輪換；完整乘積上千種留給後面只比規則的回歸。審核要求在文件裡明確寫成代表性覆蓋。
- **收益**：避免讀者把 36 種誤解成完整驗證。
- **分類**：Universal。　**L／S／E**：是／是／是。　**成熟度**：高（成本幾乎為零）。

### R5. 測試本身的錯誤與產品錯誤分開報告

- **案例**：CI #174 的另一個失敗是測試把天氣台詞「雨 22°」讀成第 22 頁——是測試的錯，不是 App。報告裡分開寫，沒有算成「發現 2 個不一致」。
- **分類**：Universal。　**L／S／E**：是／是／是。　**成熟度**：高。

### R6. 個別事件的根因與「同類事件的證據」分開記錄

- **案例**：#68／#79（launcher ANR 後點擊失效）的原始紀錄拿不到；#100 自然發生同類事件並留下證據，證實修正流程有效。審核決定：#100 記錄為「同類自然 ANR 已證實修正流程有效」，#68／#79 個別事件仍是 Unknown，只註明間接佐證。
- **收益**：結論的強度跟證據一致，不會因為「很像」就把沒看到的事件標成已解決。
- **成本**：狀態描述比較長。
- **分類**：Universal。　**L／S／E**：可省略／是／是（高風險專案尤其重要）。　**成熟度**：中。
- **待驗證**：多人協作時，大家是否會照這種區分讀狀態（還是只看「Unknown」就當成沒進展）。

### R7. 合併前先確認 base 分支自己的 CI；基礎設施失敗要先確認，不直接當成 PR 的問題，也不直接忽略

- **案例**：準備合併 P7-3 時發現 main 的 CI #172（只改 README）是紅的：141 個測試失敗，全部是 Maven Central 回 HTTP 429。P7-3 分支同樣的程式是綠的。處理：重跑一次確認，再決定能不能合併。
- **收益**：不會把別人的紅燈帶進合併判斷，也不會在紅燈上合併。
- **成本**：一次重跑。
- **分類**：Universal。　**L／S／E**：可省略／是／是。　**成熟度**：高。
- **待驗證**：外部服務限流頻繁的專案是否該改成快取依賴（Stack-specific 的後續）。

### R8. 刪分支前做 Branch Audit；squash 合併要用內容比對，不只看祖先

- **案例**：`claude/portfolio-readme` 的 commit 不是 main 的祖先（PR #2 用 squash 合併），只看 `--is-ancestor` 會誤判成「沒合併」；用 `git diff <branch> main` 確認內容完全相同才判斷可刪。另外 10 個 `acceptance/*` 是獨立歷史的人工審核素材，CI 不會重產，不能當成「沒用的分支」。
- **做法**：每個分支記錄 SHA、是否祖先、main 沒有的 commit 數、內容比對、是否有獨有證據、文件引用數；只刪「合併已驗證、main CI 綠」的。
- **分類**：Universal（做法）；門檻 Scale-dependent。　**L／S／E**：可省略（分支少）／是／是（刪除前可能還要第二人確認）。　**成熟度**：中高。
- **待驗證**：分支數上百時是否要自動化成腳本。

### R9. 驗收證據分層保存

- **案例**：正式 golden 在 main；精簡報告與少量代表圖在 `docs/`；完整 CI 輸出在每次覆蓋的 `screenshots/*` 分支；人工審核素材在 `acceptance/*`。問題是 `screenshots/*` 會被下一次 CI 覆蓋、Actions artifact 90 天過期，而有一部分證據只存在那裡（例如 #100 的截圖）。P7-3 在結案時把代表截圖複製進 `docs/`。
- **做法（提案）**：結案時決定哪些證據要永久保留，複製到 docs 或 Release assets；其他照期限過期。
- **分類**：Scale-dependent。　**L／S／E**：否（只留報告）／是（docs＋代表圖）／是（加上 Release 歸檔與期限規則）。　**成熟度**：低（還沒實際歸檔過）。
- **待驗證**：Release assets 是否適合當證據倉庫（大小、搜尋、權限）。

### R10. 階段分支用 `--no-ff` 疊在一起、PR 用 merge commit

- **案例**：P7-4a 以 `--no-ff` 併入 P7-3 分支，再整個用 merge commit 進 main；P7-4a 的 7 個 commit 都保留，合併後可以用 `--is-ancestor` 驗證刪分支是安全的。
- **分類**：Scale-dependent（也跟團隊慣例有關）。　**L／S／E**：否（squash 就好）／是／看團隊規範。　**成熟度**：中。
- **待驗證**：歷史很長時，是否反而讓 `git log` 難讀。

### R11. 測試用掛勾「正式執行時是 null」

- **案例**：`MowanBitmap.onRender`、`MowanView.onFrame`、`CalendarWidget.onUpdated`：正式執行時不記錄、不保留任何圖（避免記憶體洩漏），測試才設定。
- **分類**：Stack-specific（Kotlin／Android 的寫法）；原則可能通用。　**L／S／E**：否／視需要／視需要（Extended 可能要求審查）。　**成熟度**：低（只在這個專案用過）。

### R12. 被取代的 CI 執行要取消

- **案例**：同一個分支連續推了修正，舊 commit 的模擬器驗收（約 25 分鐘）沒有參考價值，取消以免排隊。
- **分類**：Universal（有排隊成本時）。　**L／S／E**：是／是／是。　**成熟度**：高；但要注意不要取消「唯一一次在某個 commit 上的驗收」。

### R13. 沙盒環境拿不到 artifact 時，把結果推到 git 分支

- **案例**：這個執行環境下載不了 GitHub Actions artifact（blob 主機被擋），所以 CI 把截圖與診斷資料推到 `screenshots/*` 分支，用 git 讀。
- **分類**：Project-specific（執行環境限制）。　**L／S／E**：只在同樣受限的環境。　**成熟度**：高（在這裡），但不該變成通用規則。

## 本專案專用（不升級成通用規則）

- 墨丸的 9 條顯示規則（D-41、D-44、D-55 等）、SmallEnv／簡化畫法的取捨。

- `screenshots/*`、`acceptance/*` 的命名方式。
