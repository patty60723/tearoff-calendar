# AI-Assisted Development Workflow — 研究紀錄

> 版本：2026-11-03（第 2 版）　來源：墨丸 V3 的 P7-3（狀態一致性）、P7-4a 併入、PR #3、Branch Audit、證據歸檔試點。
> 性質：**研究階段的觀察，不是最終 Skill**。每條規則都只有這一個專案的證據；「成熟度」只代表在這裡反覆有效，仍需其他專案驗證。墨丸專用的做法不寫成通用規範。
> 結構：**1. Core Principles**（跟規模、技術無關的原則）→ **2. Lite／Standard／Extended Profiles**（同一個原則在不同規模的做法與門檻）→ **3. Stack-specific Adapters**（綁技術的實作）→ **4. Environment Constraints**（綁執行環境的限制與因應）。
> 分類標記：**U**＝Universal、**S**＝Scale-dependent、**T**＝Stack-specific、**P**＝Project-specific（或執行環境限定）。
> 規則編號 R1～R13 是第 1 版的候選（保留，內容沒有刪），R14～R19 是第 2 版新增，R20～R21 是 2026-11-04 新增（P7-7 準備審核），R22 是 2026-11-04 第二次審核新增，R23 是 2026-11-04 第三次審核新增。

## 規模定義

| Profile | 適用 | 特徵 |
|---|---|---|
| **Lite** | 原型、短期工具 | 一個人、幾天到幾週、可以丟掉重來；成本比證據重要 |
| **Standard** | 持續維護的個人專案 | 一個人加 AI 助理、會持續改版、需要回歸測試與可追溯的決定（本專案） |
| **Extended** | 多人協作或高風險 | 多人審查、權限分層、合規或使用者影響大；證據要能交給別人檢查 |

## 1. Core Principles（U）

原則只描述「要達成什麼」，不指定工具與門檻（門檻在第 2 節）。

### P1. 一致性與正確性從「實際輸出」驗證（R1）

- 問題與案例：既有測試拿設定值重畫一張圖來比，等於同一份設定比兩次。P7-3 改成在真正輸出的地方回報實際用的參數，再用那組參數重畫、逐像素相同才算數；找到一個既有測試沒抓到的不一致（換城市時故事卡的天氣）。
- 收益／成本：抓到真的錯；正式程式多幾個觀察點、測試要處理歧義。
- 成熟度：中（只在圖形輸出驗證過）。
- 待驗證：非圖形輸出（API、報表）是否同樣低成本。

### P2. 先讓測試重現問題，再修（R2）

- 案例：換城市的不一致先推「會紅的測試」（CI #174），再推修正（#176）。
- 收益：證明測試抓得到；修正有紀錄。成本：多一輪 CI。
- 成熟度：高（P7-1、P7-2、P7-4a、P7-3 都有效）。
- 待驗證：CI 很慢時，本機重現是否就夠。

### P3. 把「應該相同」與「刻意不同」寫成規則表（R3）

- 案例：P7-3 列了 9 條刻意不同的顯示規則；其中一條原本只是既有行為，被提出來變成正式決策 D-55。
- 成熟度：中高。待驗證：規則多到數十條時的維護成本。

### P4. 覆蓋範圍照實描述（R4）

- 案例：36 種是代表性組合，不是完整排列；審核要求文件明寫。
- 成熟度：高（幾乎沒有成本）。

### P5. 測試本身的錯與產品的錯分開報告（R5）

- 案例：CI #174 另一個失敗是測試把天氣台詞讀成頁數；報告裡沒有算成產品的不一致。
- 成熟度：高。

### P6. 個別事件的結論與同類事件的證據分開（R6）

- 案例：#68／#79 的紀錄拿不到 → 維持 Unknown；#100 同類自然事件證實修正流程有效 → 只記成間接佐證。
- 成熟度：中。待驗證：多人時大家會不會把 Unknown 誤讀成「沒進展」。

### P7. 合併前確認 base 分支自己的狀態；基礎設施失敗要確認，不直接歸咎也不直接忽略（R7）

- 案例：main 的 CI #172（只改 README）因 Maven Central 429 紅；重跑一次確認綠了才合併 P7-3。
- 成熟度：高。

### P8. 刪除前先 Audit，刪除後再驗證（R8）

- 案例：逐一記錄分支的 SHA、是否祖先、獨有 commit、獨有證據、文件引用；只刪「合併已驗證、main CI 綠」的。
- 成熟度：中高。待驗證：分支上百時要不要自動化。

### P9. 證據分層保存（R9）

- 案例：golden 在 main、精簡報告在 docs、完整輸出在會被覆蓋的分支、人工審核素材在獨立分支；有些證據只存在會過期或被覆蓋的地方。
- 成熟度：低（歸檔還沒真正完成，見 P13）。

### P10.（新）Audit 要分「歷史快照」與「目前狀態」（R14）

- 問題與案例：第一版 Branch Audit 寫在合併前，裡面的「本輪刪除」是建議；合併後分支其實刪不掉（權限）。如果直接改那份文件，就看不出當時根據什麼做判斷；如果不改，讀者會以為已經刪了。
- 做法：合併前的 Audit 保留不改、標成快照；另寫一份合併後的實際狀態（實際 SHA、驗證結果、沒做成的事）。
- 收益：決策可追溯；不會把建議誤讀成結果。成本：多一份文件、要互相連結。
- 成熟度：中。待驗證：Audit 很頻繁時，是否改成一份文件加「時間軸」比較好。

### P11.（新）squash 合併的安全判斷不能只靠祖先關係或目前的 tree diff（R15）

- 問題與案例：`claude/portfolio-readme` 的 commit 不是 main 的祖先（squash），第一版改用「`git diff <分支> main` 是空的」判斷可刪。但目前的 tree diff 只比兩個快照：main 之後的修改可能剛好讓 diff 變空（或變不空），分支在 squash 後也可能又加了 commit，而且分支外的證據（CI 輸出）diff 看不到。
- 做法：同時看 (1) PR 紀錄（合併方式、merge commit）、(2) 分支現在的 SHA＝PR 合併時的 head、(3) 合併當時的 base 與「base → head」等於「base → squash commit」、(4) 有沒有獨有證據；目前的 tree diff 只當輔助。
- 收益：不會誤刪 squash 之後又推過 commit 的分支。成本：要查 PR API。
- 成熟度：中（只驗證過一個 squash PR）。
- 待驗證：一個 PR 有很多 commit、或 PR 合併後 base 又被 force-push 的情況。

### P12.（新）權限不足時安全停止，交出人工步驟（R16）

- 問題與案例：刪除遠端分支（git proxy 403、REST 403）、建立 Release（403）都被擋。沒有嘗試其他路徑繞過；把要刪的分支、前置驗證、網頁上的操作步驟、刪錯時怎麼復原寫清楚，交給人。
- 收益：不會用意料外的方式改動共享狀態；人工步驟可以照做。成本：工作停在「待人工」。
- 成熟度：高（原則本身沒有爭議）；**怎麼判斷「這是繞過」** 仍需要更多案例（例如：改用另一個官方 API 算不算繞過）。

### P13.（新）證據歸檔必須驗證「拿得回來」與「內容一致」（R17）

- 問題與案例：試點把 `acceptance/mowan-p5-2` 打包成 ZIP、產生 SHA-256 與逐檔 manifest；上傳被權限擋下，所以狀態是 **Archive Verification Pending**，不宣稱歸檔完成。另外，下載驗證的路徑可以用（拿既有的 App asset 試過）。檢查工具本身的測試也抓到一個錯：壞掉的 ZIP 會讓檢查程式當掉，而不是回報失敗。
- 做法：上傳 → 重新下載 → SHA-256 → 檔案數不多不少 → 逐檔內容 → 穩定連結可用；全部通過才算完成，之前原始證據不刪。驗證用的雜湊與 manifest 放在 repo（不信任歸檔位置上的說明文字）。
- 成熟度：中（流程有，但還沒完整跑過一次）。
- 待驗證：大檔案（數百 MB）時的時間與成本；Release 被編輯、asset 被替換的偵測。

### P14.（新）Universal 原則與 Scale-dependent 實作分開寫（R18）

- 問題與案例：第 1 版把「用 `--no-ff` 疊階段分支」寫成候選規則，但那其實是這個專案的偏好；同一個原則（「合併後能驗證整合了什麼」）在別的專案可以用 squash＋PR 紀錄達成。
- 做法：原則寫「要達成什麼」，實作與門檻放進 Profile 或 Adapter。
- 成熟度：中（這份文件的結構本身就是這條規則的試驗）。

### P15.（新）驗收同時檢查「功能正確」與「品質退化」（R20）

- 問題與案例：P7-7 準備的候選 A（日曆頁留夠空間）**功能上完全正確**——不重疊、字體 100% 逐像素不變、測試全過；但審核指出在 320dp × 200% 時日期數字從 88dp 縮成 52dp，視覺階層明顯退化。只看「重疊＝0」的測試抓不到這個問題，所以補了候選 C（頁面跟著加高，日期不縮），並把日期大小、間距、截斷一起列進量測表。
- 做法：修正的驗收除了「問題消失」，還要量修正**可能犧牲的東西**（主要資訊的大小、間距、截斷、遮擋），並跟現況並排比較；能量化的寫成數字，不能量化的放進人工視覺審核。
- 收益：避免「修好一個問題、悄悄造成另一個」。成本：每個候選要多量幾個指標、多一輪審核。
- Profile：Lite＝看圖確認即可；Standard＝主要指標寫進量測表（本專案）；Extended＝退化指標設門檻（例如日期字高不小於某個比例）並納入自動測試。
- 成熟度：中。**需要跨專案驗證**：怎麼挑「可能犧牲的指標」，在非 UI 的專案（例如效能修正犧牲記憶體）是否同樣適用。

### P16.（新）準備階段通過 ≠ 正式實作驗收通過（R21）

- 問題與案例：P7-7 準備階段通過了審核（候選方向、對比門檻、golden 影響範圍），但審核明確要求正式實作前再補兩個候選、量清楚共用色的影響；準備階段的候選圖是在**測試裡改 View 組出來**的，不是正式程式——正式實作時版面檔、程式、golden 更新、模擬器驗收都還要重做一次驗收。
- 做法：每個階段的狀態分開寫（「準備：通過」「正式實作：未開始」）；正式實作的驗收條件在準備階段就寫好，但不能拿準備階段的結果直接當成實作的證據。
- 收益：不會把「方向核准」誤讀成「已完成」。成本：狀態描述多一層。
- Profile：Lite＝可以合併成一次審核；Standard＝分開（本專案）；Extended＝分開，且實作驗收要由另一個人做。
- 成熟度：中高（本專案 P7-1、P7-2、P7-7 都是「先候選、後實作」）。**需要跨專案驗證**：在沒有獨立準備階段的流程（例如直接開 PR 討論）是否仍需要這個區分。

### P17.（新）多次局部修正都達不到驗收條件時，回頭檢查結構性限制與需求取捨（R22）

- 問題與案例：最小 TALL 小工具（150×250dp）在字體 200% 時日期看不到、文字重疊。連續試了 5 個局部修正——T1 搬天氣三行、T2 換位置、T3 限制倍率 1.3、T4＝T3＋T1、T5＝T3＋日期縮放下限改 dp——每一個都只把問題移到別處（日落被擠出外框、日期被切、碰到英文月份）。審核要求不要再把 T5 的倍率從 1.3 改成 1.2 就當解決，而是先把**垂直空間逐項列出來**（哪些固定、哪些跟著字體放大、日期還剩多少），再做結構重配（T6）與明說代價的有限倍率（T7），並量出「要多高才夠」的替代方案。
- 做法：當同一類修正連續兩、三次都失敗，而且失敗的形態是「問題換個位置出現」時：(1) 停止微調；(2) 把資源（空間、時間、記憶體、預算）逐項量化，分出固定與可以重新分配的部分；(3) 算出在現在的限制下**理論上能不能滿足**；(4) 不能時，列出可量化的取捨（例如提高最小尺寸、放寬某個條件），交給人決定。
- 何時停止微調（候選訊號）：修正讓指標 A 變好但 B 變差；同一個參數第二次被往同一個方向調；或者量化之後發現需求總和本來就超過資源。
- 何時需要人類決策放寬需求：資源量化後確定不夠；任何解法都要犧牲一個「不得」條件（例如隱藏資訊、降低字體倍率）；或解法影響範圍超出原本的變更（例如提高最小高度影響所有使用者）。
- 收益：避免在不可能的空間裡無限試錯；把「技術問題」轉成「需求取捨」，交給有權限的人。成本：量化本身要做一輪（這次是一個測試加一輪 CI）。
- Profile：Lite＝試兩次不行就換方向，不必量化；Standard＝量化資源、列出取捨（本專案）；Extended＝量化結果與取捨要寫進決策紀錄，放寬需求要有負責人簽核。
- 成熟度：中（本專案只有這一次完整的例子）。**需要跨專案驗證**：「連續幾次失敗」的門檻、在非 UI 的資源（效能、記憶體）是否同樣好量化。

### P18.（新）研究階段修正了測試方法，正式實作計畫與驗收條件要同步更新（R23）

- 問題與案例：P7-7 研究階段先後發現兩種量法會誤判——TextView 邊界（字距留白造成「截斷：天氣」誤報）、`Paint.getTextBounds`（`letterSpacing` 的留白被算進字形，「英文月份被切 2%」）——研究文件 §9.1 已改成「實際畫出來的像素」。但同一天寫的正式實作計畫 §5 還寫著「用 `Paint.getTextBounds`」。照計畫實作，就會把研究階段已經證明會誤報的方法寫進正式測試。審核時才發現。
- 做法：
  1. 研究文件裡「量法變更」要有固定的段落（本專案是 §9.1 的表：舊量法、問題、新量法、影響）。
  2. 量法變更時，找出所有引用舊量法的文件與測試（計畫、驗收條件、測試工具），同一個 commit 一起改；改不了的寫明「待同步」。
  3. 正式實作的測試要包含**重現舊量法誤報與漏報的回歸測試**（新量法要分得出來，舊量法要真的會錯），避免之後有人換回舊方法。
- 可以自動檢查的條件（候選）：
  - 文件裡出現研究文件標成「已淘汰」的量法名稱（例如 `getTextBounds`）而且不在「舊量法」的段落 → 警告。
  - 正式計畫的「測試方法」段落要連到研究文件的「量法變更」段落；連結的版本（commit）比研究文件最後一次修改舊 → 警告。
  - 測試原始碼裡呼叫已淘汰的 API 做判斷（例如 `getTextBounds` 出現在截斷判斷）→ 測試或 lint 失敗；回歸測試本身（故意重現舊量法）用註記排除。
- 收益：研究的修正真的進到正式驗收；之後的審核不必重新比對兩份文件。成本：要維護「已淘汰量法」清單與一個簡單的文字檢查。
- Profile：Lite＝研究與計畫在同一份文件，改量法時順手改；Standard＝量法變更表＋同一個 commit 同步計畫與測試（本專案）；Extended＝已淘汰量法清單＋自動檢查（文字 grep 或 lint）＋回歸測試是驗收的必要項目。
- 成熟度：中（本專案發生一次，已在 P7-7 正式計畫修正）。**需要跨專案驗證**：自動檢查的誤報率（同一個 API 也有正當用途）。

## 2. Lite／Standard／Extended Profiles（S）

| 原則 | Lite | Standard | Extended |
|---|---|---|---|
| P1 實際輸出驗證 | 不需要（手動看一眼） | 多個呈現位置共用狀態時做 | 做，觀察點要經過審查 |
| P2 先重現再修 | 建議（本機重現即可） | 必要（CI 紅一次再綠） | 必要，紅燈的 CI 連結附在 PR |
| P3 規則表 | 不需要 | 有多個呈現位置時寫 | 必要，規則要有決策編號 |
| P4 覆蓋範圍照實描述 | 必要（成本幾乎為零） | 必要 | 必要 |
| P5 測試錯與產品錯分開 | 必要 | 必要 | 必要 |
| P6 個別結論與同類證據分開 | 可省略 | 必要 | 必要，加上誰同意升級結論 |
| P7 base 狀態 | 可省略 | 必要（重跑一次確認） | 必要，加上保護分支規則 |
| P8 刪除前 Audit | 可省略（分支少） | 必要（本專案的表格） | 必要，刪除要第二人確認 |
| P9 證據分層 | 只留報告 | 報告＋代表圖在 docs；完整輸出有期限 | 加上里程碑歸檔、保存期限政策 |
| P10 快照與現況 | 不需要 | 有 Audit 時做 | 必要 |
| P11 squash 判斷 | 可省略 | 必要（有 squash 合併時） | 必要，自動化檢查 |
| P12 權限不足時停止 | 必要 | 必要 | 必要 |
| P13 歸檔驗證 | 不需要（不歸檔） | 必要（有歸檔時） | 必要，加上定期抽查 |
| P14 原則與實作分開 | — | 寫流程文件時做 | 必要 |
| P15 功能正確＋品質退化 | 看圖確認 | 退化指標寫進量測表 | 退化指標設門檻、自動測試 |
| P16 準備 ≠ 實作驗收 | 可以合併 | 分開寫狀態與驗收 | 分開，實作由另一人驗收 |
| P17 局部修正失敗→檢查結構 | 試兩次不行就換方向 | 量化資源、列出取捨 | 量化寫進決策紀錄，放寬需求要簽核 |
| P18 量法變更同步到計畫與驗收 | 同一份文件順手改 | 量法變更表＋同一個 commit 同步、回歸測試 | 已淘汰量法清單＋自動檢查＋回歸測試必要 |

### R19.（新）合併策略要可設定，不一律要求 `--no-ff`

- 問題與案例：本專案用 `--no-ff` 把 P7-4a 疊進 P7-3、再用 merge commit 進 main（見 R10），好處是能用祖先關係驗證刪分支安全；但同一個 repo 的 PR #2 用了 squash，也是合理的（只有一個 README commit）。
- 做法（提案）：每個專案（或每種變更）設定合併策略：`merge`（保留階段歷史、可用祖先驗證）、`squash`（歷史乾淨，刪分支前要用 P11 的方式驗證）、`rebase`。Profile 只給預設：Lite＝squash，Standard＝依變更大小（階段性工作用 merge、單一小修正用 squash），Extended＝照團隊規範。
- 成熟度：低（只是從兩個 PR 的對比推出來的）。
- 待驗證：在採用 squash 為主的專案，P8／P11 的成本是否可以接受。

### R10（第 1 版，已由 R19 修訂）階段分支用 `--no-ff`、PR 用 merge commit

- 原內容：P7-4a 以 `--no-ff` 併入 P7-3，再用 merge commit 進 main，所有 commit 保留，合併後可以用 `--is-ancestor` 驗證。
- 修訂：這是本專案（Standard）的**一種設定**，不是通用規則；見 R19。

### R12 被取代的 CI 執行要取消（S）

- 案例：同一個分支連續推修正時，取消舊 commit 的長時間驗收（約 25 分鐘）。
- Profile：Lite／Standard／Extended 都適用（有排隊成本時）；**例外**：某個 commit 唯一一次的驗收不能取消。成熟度：高。

## 4. Environment Constraints（P，執行環境限定）

這些是**這個執行環境**的限制，不能寫成通用規則；Skill 應該把它們當成「偵測到時怎麼辦」。

| 限制 | 影響 | 因應（本專案） |
|---|---|---|
| Actions artifact 下載不了（blob 主機被網路政策擋） | 看不到 CI 的截圖與紀錄 | CI 把結果推到 `screenshots/*` 分支，用 git 讀（R13） |
| GitHub GraphQL 不能用 | `gh pr view`、`gh release list` 失敗 | 改用 REST（`gh api repos/...`） |
| 刪除遠端分支被擋（git proxy 403、REST 403） | 合併後不能清分支 | 停止、列出待人工處理的分支與步驟（P12） |
| 建立／編輯 Release 被擋（403） | 不能上傳歸檔 | Archive Verification Pending、交出上傳步驟（P12、P13） |
| Release asset 可以下載（REST） | 人工上傳後可以驗證 | 下一輪做下載驗證 |
| 這個 clone 的 `git fetch` 不會自動更新遠端追蹤分支 | 本機以為有「沒推上去的 commit」 | 用 `git ls-remote` 對 SHA、明確指定 refspec 抓 |
| 外部套件庫限流（Maven Central 429） | CI 隨機紅 | 重跑一次確認（P7）；長期可考慮快取（T） |
