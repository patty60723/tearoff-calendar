## 2. 編號說明：P7-4 與 ANR

P7 計畫裡的 **P7-4 是「相容性」**（API 26／28／30／33／34、launcher、尺寸、WIDE），不是 ANR。#68／#79 會掛到 P7-4，是因為它發生在模擬器的 Pixel Launcher 上（§5），屬於「模擬器與 launcher 環境」這一類；P7-4 的 Android 版本矩陣會讓模擬器執行次數變成好幾倍，這個問題不先釐清，矩陣結果會很難判讀。

**建議（需要你決定，§8 第 1 題）**：P7-4 分成兩個停點，不重新編號其他階段：

- **P7-4a**：ANR／點擊失效診斷（只改模擬器腳本與 workflow，不改 App）
- **P7-4b**：原計畫的相容性矩陣

## 4. 優先順序評估

| 項目 | 使用者影響 | 穩定性／證據可靠度 | 相依 | 修改風險 |

### 建議順序

1. **P7-4a ANR／點擊失效診斷**（只改腳本）——你也說原則上先釐清；而且它決定後面所有模擬器證據能不能信。
2. **P7-3 一致性**（自動測試先，模擬器部分接在 P7-4a 之後）——原計畫順序，風險低。
3. **P7-7 版面部分**（D-54、WIDE 對比）——使用者影響最高的已知問題；放在 P7-4b 前，避免相容性截圖做兩次。WIDE 對比會改 golden，需要你另外核准新基準。
4. **P7-4b 相容性矩陣**。
5. **P7-5 跨午夜**、**P7-6 效能**。
6. **P7-8 完整回歸**、P7 結案。

不依順序、可以並行：**D-52 App 圖示**（只出候選圖等美術審核）；**實機＋TalkBack**（建議集中成兩次：P7-7 之後一次——涵蓋 P7-2 的觸控與過渡、P7-7 的 TalkBack 與 200% 字體；P7-8 之前一次）。

> 跟原計畫的差別只有：P7-7 的版面部分往前移到 P7-4b 之前（P7-7 的 TalkBack 檢查清單、Reduced Motion 等其他內容照原位置也可以）。要不要這樣調整請你決定（§8 第 2 題）。

### 5.5 最小範圍的重現與診斷方案（P7-4a，只改腳本與 workflow，不改 App）

1. **先看已有的證據**（不用跑任何東西）：請你從上面三個連結下載 #78／#79 的 artifact，看 `ui/bundle-*-miss-*.txt`（`mCurrentFocus`、`mFocusedApp`、`dumpsys input` 的 FocusedWindow／TouchedWindow）。或者在這個環境的網路設定允許 GitHub artifact 的下載主機，我來讀。這一步可能直接分出 B 或 C。
2. **強制重現（決定性）**：在模擬器上用 `adb root` 把 Pixel Launcher 暫停（`kill -STOP`），對 launcher 送一個按鍵觸發它的 ANR → 出現同樣的「沒有回應」對話框 → 用現有的 `handle_anr` 關掉 → 回到我們的 App 點包袱。重複 N 次（例如 10 次），另外一組不觸發 ANR 當對照。
   - 對照組全部通過、ANR 組失敗 → 是「launcher ANR 之後的系統狀態」，跟 App 無關的機率很高；再看 `dumpsys input` 確認點擊送到哪裡。
   - 兩組都通過 → 真實的 ANR 不是這樣，回到被動收集。
3. **加強被動證據**（每次對話框出現時自動存，放在 job log 裡而不是只放 artifact）：`dumpsys input` 的 dispatcher 狀態（我們視窗的 `WaitQueue` 長度：**長度一直增加 → 我們的 App 沒在處理輸入（C）**；是 0 → 點擊沒送到我們這裡（B））、`dumpsys window` 焦點、`logcat -b events am_anr`、`/data/anr/` 的 traces（root）、點擊前後的 `getevent` 確認事件有送出。
4. **把診斷跟驗收分開**：重現用獨立的 workflow（`workflow_dispatch`），不加進日常的驗收；日常驗收照樣「有 FAIL 就 FAIL」，**不加無限制重試**。
